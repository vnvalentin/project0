## Approved planning update

### Contract Decisions
Role-specific proposal payloads are bounded as follows:
- **World DM:** `campaign_refs`, `faction_refs`, `region_refs`, `global_event_refs`, `cross_character_refs`.
- **Party DM:** `party_id`, `shared_objective_refs`, `relationship_refs`, `encounter_refs`.
- **Personal DM:** `character_id`, `memory_refs`, `private_hook_refs`, explicitly selected `party_refs`, and explicitly selected `world_bulletin_refs`.

Every field is a bounded reference or validated semantic value. No role may include another role’s private fields. Missing required fields reject; optional fields become empty lists and are never inferred.

### Measurable Component
Validate the exact role-specific field allowlist and bounds; reject missing required fields and cross-role private fields; represent omitted optional fields as explicit empty lists, with no inference.


## Authority precedence and bounded outcomes

### Contract Decisions
Authority precedence, highest to lowest: server-owned authoritative state > World DM proposal > Party DM proposal > Personal DM proposal > client input/presentation. Within one role/scope, order by canonical event sequence then stable proposal ID. Lower priority cannot overwrite higher priority. A same-priority same-field conflict returns `CONFLICT` and applies no mutation.

### Measurable Component
The full bounded outcome vocabulary is `MALFORMED`, `UNSUPPORTED_SCHEMA`, `MISSING_REQUIRED_FIELD`, `INVALID_FIELD`, `UNAUTHORIZED_SCOPE`, `PRIVATE_CONTEXT_FORBIDDEN`, `AMBIGUOUS_INTENT`, `STALE_SNAPSHOT`, `CONFLICT`, `CONTEXT_UNAVAILABLE`, `TOO_LARGE`, `FALLBACK`. Each result carries only `outcome`, `reason_code`, `schema_version`, and a correlation/provenance reference. Raw prompts and unrestricted model output never enter error payloads.


## Version and provenance contract
All proposals carry server-owned `schema_version`, `contract_version`, `prompt_version`, `model_id`, `model_version`, `builder_version`, `tuning_version`, `input_snapshot_hash`, and `provenance_id`. A proposal is stale/invalid when any required version differs from the active contract or when the input snapshot hash no longer matches; the server never silently migrates proposals across versions.

Provenance is bounded to `proposal_id`, `source_role`, `requesting_scope`, `input_snapshot_hash`, schema/contract/prompt/model versions, `canonical_event_sequence`, `outcome`, `reason_code`, `normalized_output_hash`, timestamps, and `correlation_id`. Raw prompts, credentials, private context, and unrestricted generated text are not persisted in provenance. Normalized bounded proposal content is retained separately only after validation and under storage policy.

## Version and Provenance — measurable component
Measure the percentage of proposals with all server-owned fields, matching input snapshots, valid bounded provenance, and denylisted fields absent; target 100% for accepted proposals and 100% rejection for invalid cases.

## Validation experiments
Exercise each version mismatch and input snapshot mismatch, confirming stale/invalid rejection with an explicit reason code and no silent migration. Attempt provenance denylisting for raw prompts, credentials, private context, and unrestricted model output; confirm rejection, bounded normalized output handling, and correlation/provenance traceability.

## Approved retention, replay, active-version, and promotion policy

- Validated normalized proposals and bounded provenance are retained for the lifetime of the related Canon revision plus its audit-retention window. Rejected proposals are retained only as bounded metadata for 30 days. Raw prompts, credentials, private context, and unrestricted model output are never retained.
- Replay is allowed only when schema, contract, prompt, model, builder, tuning, and input snapshot versions match. Expired or mismatched records return `STALE_SNAPSHOT` or `UNSUPPORTED_SCHEMA` and are never silently regenerated.
- The server owns one active version tuple: schema, contract, prompt, model, builder, and tuning versions. Activation and rollback are explicit, versioned, and auditable; proposals using inactive tuples reject with `UNSUPPORTED_SCHEMA` or a stale-version outcome.

### Promotion evidence
Promotion requires every normal, invalid, boundary, conflict, stale-version, and privacy case to pass; two independent runs with identical normalized output and snapshot hashes; a retained machine-readable fixture artifact; exit 0, zero failed assertions, and zero missing test cases. Results are posted to the Experiment issue with command, commit, artifact path/hash, and timestamp. Promotion is blocked until evidence is attached and reviewed.

### Measurable Component
Measure retention denylist enforcement, exact active-tuple matching, deterministic replay, and complete promotion evidence at 100%: no forbidden data retained, no silent regeneration, identical two-run hashes, retained artifact, and zero missing or failed cases.
