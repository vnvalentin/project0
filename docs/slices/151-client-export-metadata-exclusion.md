## User outcome

The packaged Windows client no longer carries editor/import metadata that points
at server-only GDExtensions. Its boot log is now usable evidence during update
and rollback testing rather than containing three expected SQLite extension
errors.

## Root cause and fix

The Windows preset already excluded `addons/godot-sqlite/**`, correctly keeping
the server-only SQLite engine out of the client. However, its `all_resources`
export still included `.godot/extension_list.cfg`, generated by the editor. That
metadata referenced `res://addons/godot-sqlite/gdsqlite.gdextension`, so the
packaged client tried to load an extension whose binary had intentionally been
excluded.

Fix: add `.godot/**` to `export_presets.cfg`'s `exclude_filter` and temporarily
move the server-only `gdsqlite.gdextension` declaration plus generated extension
cache outside the project during `export_windows_client.sh`, restoring both in
the exit trap. This preserves the server/client boundary and removes the stale
editor declaration; it does not ship SQLite to the client or weaken the server
export.

## Scope and non-goals

In scope: Windows export filtering and DT-015 closure.

Out of scope: changing the server's SQLite extension, changing the client
runtime, the updater orchestration, the `/patches` hosting route, or controller
support.

## Validation

- Pre-fix fresh Windows export proved the cause by showing
  `.godot/extension_list.cfg` in the pack's `savepack` list.
- The fixed export temporarily hides both the server-only
  `addons/godot-sqlite/gdsqlite.gdextension` declaration and the generated
  `.godot/extension_list.cfg` outside the project tree, then restores both via
  the export script's exit trap. The fixed export log contains **no `gdsqlite` /
  `godot-sqlite` references**; the remaining extension entry is the separate
  wgnetstack client path, outside DT-015.
- The fresh exported `Project0.exe --headless` boot produced **zero
  `gdsqlite`, `godot-sqlite`, or `sqlite` log lines**. The bounded probe ended at
  the expected 8-second timeout (`exit 124`), not from an SQLite load failure.
- Fresh fixed export evidence: `Project0.exe` and `Project0.pck` were produced;
  the export log contained no `gdsqlite` / `godot-sqlite` references; both the
  SQLite declaration and `.godot/extension_list.cfg` were restored afterward.
- `bash scripts/run_gut_validation.sh` remains the regression command; no
  GDScript behavior changed.
- `bash scripts/check_record_sync.sh` exits 0.

## Root-cause learning

No unexpected implementation failure. The defect was found by running the real
packaged client during the Slice 149 Windows pack probe, not by source inspection:
the export exclusion for the addon was correct, but editor-generated `.godot`
metadata bypassed the intended boundary. Countermeasure: export filters now
explicitly exclude editor/import metadata, and future packaged-client probes must
inspect the actual pack contents rather than infer them from source filters.

A separate environment issue occurred during the fresh export: the Godot export
completed, but the script's ZIP fallback could not find Python on Windows after
`zip` was unavailable. That packaging-tooling issue is not folded into this
slice's DT-015 fix; the exported directory is sufficient to inspect the pack,
and a later packaging-tool slice should make the Windows fallback explicit.
